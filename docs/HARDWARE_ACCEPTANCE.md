# 硬件验收清单（V1 收尾）

本清单交给 Founder 在实板上执行。下面每一项的状态都是 **未在硬件上执行**。仓库里的主机测试和 SDCC 链接不能代替烧录、串口、LED 或急停。

记录日期：2026-11-18 12:57（北京时间）。链接数字来自本机 SDCC 4.2.0 #13081，命令是 `make -C firmware PLATFORM=8051`。没有把芯片放进编程器，也没有读过片内 RAM。

假定的板子与现有固件注释一致：STC89C52（8052 内核，有高 128 字节间接 RAM）、11.0592 MHz、12T。若板上芯片不是这个型号，先停下来，不要烧这份 HEX。

## 1. 烧录

状态：**未在硬件上执行。**

步骤：

1. 在 Linux 上安装 SDCC 和 make，于仓库根目录执行 `make -C firmware PLATFORM=8051`。
2. 确认生成 `firmware/build/firmware.hex`，并用 `python3 scripts/validate_intel_hex.py firmware/build/firmware.hex` 看到校验通过。
3. MCU 断电。USB-TTL 的 TX 接 MCU RX（P3.0），RX 接 MCU TX（P3.1），共地。不要在通电时热插电平不匹配的线。
4. 用已有脚本烧录，不要换新工具：`python scripts/flash_mcu.py firmware/build/firmware.hex --port COMx --tool stcgal`。脚本会等回车，然后提示给 MCU 上电。stcgal 波特率按脚本现有参数 115200，这是编程口波特率，不是运行时串口波特率。
5. 也可以按 `python scripts/flash_mcu.py --keil-guide` 或 `make -C firmware PLATFORM=8051 flash` 打印的 STC-ISP 步骤手工下载同一份 HEX。

预期结果：编程器报告成功，复位后运行灯 P3.4 被拉低（低电平点亮），错误灯 P3.5 为高（灭），点阵全灭。若编程器报错或芯片型号不对，停止后续步骤。本项没有在实板上做过。

## 2. 串口参数

状态：**未在硬件上执行。**

运行时串口是 9600 波特、8 数据位、无校验、1 停止位。固件在 `HAL_UART_INIT` 里把 T1 设为模式 2，SMOD=0，TH1=0xFD，这是 11.0592 MHz、12T 下的 9600。PC 侧新执行器同样打开 9600-8N1，无流控。

步骤：复位开发板。用串口助手或 MotionControl 打开同一端口，参数设成 9600-8N1。先不要发数据。

预期结果：线上空闲为高，没有自发的 `CC`。发一个字节 `00`，板子不回任何字节，点阵保持全灭。本项没有在实板上做过。

## 3. 帧格式与三条运动指令

每帧固定 10 字节：`AA`、运动类型、X 大端、Y 大端、Vx、Vy、保留字节、前 9 字节的 XOR。运动类型只接受 0 直线、1 圆弧、2 正弦。新的 MotionControl 只发 0 和 1，速度和保留字节为 0。旧示例还会发 2。没有单独的“等待”帧；等待在 PC 上是重复坐标。

ACK 是 `CC` 加 1 字节序号。`frame_seq` 从 0 开始，成功出队后先加 1 再发送，所以复位后第一帧的 ACK 是 `CC 01`，之后 `CC 02`。序号到 255 之后下一帧是 `CC 00`。ACK 只表示固件收下了这一帧，不是位置反馈。队列里已有的帧会按顺序点亮并各自 ACK。

下面三帧的坐标按固件 `led_plot_point` 计算。点阵行由 P0 位选、列由 P1 位输出。代码把量化 Y 翻转到 framebuffer，所以数学上的 Y=0 写进行 7。哪一条物理边是“下”，取决于排线，下表写的是端口位，不是已经看见的灯。

| 指令 | 发送的 10 字节 | 预期 ACK | 预期 LED |
|---|---|---|---|
| 直线，量化 (0,0) | `AA 00 00 00 00 00 00 00 00 AA` | 复位后的第一帧：`CC 01` | framebuffer 第 7 行 bit0：P0.7 选通时 P1.0 为 1，其余行为 0 |
| 圆弧，量化 (65535,65535) | `AA 01 FF FF FF FF 00 00 00 AB` | 若它是第二帧：`CC 02` | framebuffer 第 0 行 bit7：P0.0 选通时 P1.7 为 1 |
| 正弦，量化 (32768,32768) | `AA 02 80 00 80 00 00 00 00 A8` | 若它是第三帧：`CC 03` | framebuffer 第 3 行 bit4：P0.3 选通时 P1.4 为 1 |

状态：**未在硬件上执行。**

步骤：每发一帧前确认上一帧的 ACK 已经收到。用示波器或逻辑分析仪看 P0/P1，也可以直接看点阵，但要记下排线方向。三帧之间不要插入别的字节。

预期结果：每帧恰好 2 字节 ACK，序号连续；点阵上同时只有一个点，位置与上表的端口位一致。若序号跳变或灯不在该位，停止并复位，不要重发整段轨迹。本项没有在实板上做过。

## 4. 急停

状态：**未在硬件上执行。**

急停是 P3.2，低电平有效。INT0 设为下降沿；主循环也会读 P3.2。两者都会把 `system_running` 清零，然后进入 `emergency_stop`：关掉 T0（TR0=0、ET0=0），清空 framebuffer，P0 写 0，运行灯灭（P3.4 高），错误灯亮（P3.5 低），之后停在空循环里。协议里没有远程急停字节。PC 上 Ctrl+C 只停止后续发送，不会让固件进入这个状态。

步骤：先发第 3 节的直线帧，确认 `CC 01` 和对应的点。按住急停键或把 P3.2 拉低。再发圆弧帧。

预期结果：按下后点阵熄灭，运行灯灭，错误灯亮，圆弧帧没有 ACK。松开按键也不会恢复，必须断电或复位。本项没有在实板上做过。

## 5. 异常指令

状态：**未在硬件上执行。** 主机上的 `test_firmware_protocol` 覆盖了同一套解析规则，但没有经过 UART 和灯。

复位后再做每一行。错误灯在这些拒绝路径上不会被点亮；只有队列满或急停才会点错误灯。

| 输入 | 步骤 | 预期结果 |
|---|---|---|
| 校验错误 | 发送 `AA 00 00 00 00 00 00 00 00 00`（最后一字节应为 `AA`） | 无 ACK，点阵不变 |
| 未知运动类型 3 | 发送 `AA 03 00 00 00 00 00 00 00 A9` | 无 ACK，点阵不变。这一帧校验是对的，固件整帧丢掉，不在帧内重新找 `AA`，后面紧跟的合法帧仍能对齐 |
| 半帧 | 只发前 9 字节 `AA 00 00 00 00 00 00 00 00`，等 1 秒 | 无 ACK。再补 `AA` 后应得到这一帧的 ACK，并点亮 (0,0) |
| 超长噪声 | 先发 200 个 `00`，再发直线帧 | 噪声被丢弃；直线帧仍有 ACK 和对应的点 |
| 错位的 `AA` | 先发 `AA 10 20 30`，再发一条完整合法帧 | 前 10 字节校验失败时，固件从窗口里的下一个 `AA` 重新对齐，合法帧仍有 ACK。若前 10 字节碰巧校验通过，则不能用这组字节做本项 |
| 队列满 | 不等 ACK，连续发 9 帧合法直线帧 | 前 8 帧最终各有一个 ACK 并依次点亮；第 9 帧无 ACK，错误灯亮。当前 PC 执行器是逐帧等 ACK 的，正常使用到不了这一步 |

## 6. 栈和内存：链接结果与实测方法

状态：**链接结果已在本机读到；片内高水位未在硬件上执行。**

2026-11-18 的 `firmware/build/firmware.mem`：

| 区域 | 链接结果 | 余量 |
|---|---|---|
| DSEG（直接寻址 RAM） | 127 字节 | 最大空洞 1 字节，位于 `0x1F`。再增加一个直接寻址变量就会再次链接失败。这是不足 |
| OSEG（覆盖区，算在直接 RAM 里） | 11 字节，起点 `0x14` | 与库函数参数共用，不是空闲 |
| ISEG | 59 字节，起点 `0x69` | 8 帧 `frame_queue`。STC89C52 才有这段间接 RAM；128 字节的老 8051 不能用 |
| 硬件栈 | 起点 `0xA4`，SP 初值 `0xA3`，可用 92 字节 | 见下面的粗估。92 字节是空区间，不是测到的余量 |
| XDATA | 0 | 链接器 Max 写成 65536，板上没有外扩 RAM 时不能当空闲空间用 |
| PAGED EXT. RAM | 0 | 同上，Max 256 不是板上的空闲 |
| CODE | `0x0000`–`0x0A3D`，链接器记 2622 字节 | 链接器 Max 65536 是地址空间。按假定的 8KB Flash，还剩 5570 字节。没有核对芯片丝印 |

同一份 HEX 经 `validate_intel_hex.py` 为 175 条记录、2617 个数据字节。和链接器的 2622 差 5 字节，以 `.mem` 的区间为准，校验器只数 HEX 里的数据记录。SHA-256：`firmware.hex` 为 `72f550de1ed264601bbb03ba92c7cb85e2578978874177beb0fdb36d5b07de93`，`firmware.ihx` 为 `8544e99bee69a3b7123d0adbc8ec5921a489c527024f4613376a06a383b9dab0`。

栈的粗估方法（不是实测）：

1. 这次 SDCC 没有开 `--stack-auto`。局部变量在 DSEG/OSEG，不在硬件栈上。硬件栈只计 `lcall` 的 2 字节返回地址和源码里看得见的 `push`。
2. 启动代码是 `ljmp _main`，没有留下返回地址。
3. INT0 和 T0 都没有改优先级，不能互相打断。INT0 的编译结果几乎没有软件压栈，硬件进中断仍会压 2 字节 PC。更坏的是 T0。
4. T0 进中断时硬件压 PC（2），软件再压 `bits、ACC、B、DPL、DPH、R0–R7、PSW`（14），然后 `lcall led_scan_row`（2）。`led_scan_row` 自身不再调用。中断体合计 18 字节。
5. 主循环最深的一条链是收帧：主循环先压 4 个寄存器再调用 `protocol_feed`（2）。合法帧用尾调用进入 `on_frame_received`，不再多一层返回地址；接着 `queue_push`（2）压 3 个寄存器并调用 `memcpy`（2），`memcpy` 再调用 `__gptrget`（2）。主循环侧 15 字节。T0 若打在 `__gptrget` 里，合计 15+18=33 字节。
6. 点亮路径更浅：主循环的 4 个寄存器跨过 `led_plot_point`，第一次 32 位乘法再压 2 个寄存器并调用 `__mullong`。`__mullong` / `__divulong` 的小模型汇编本身不再压栈。加上 T0 约 28 字节。

按这条读法，92 字节里粗算用到 33，还剩约 59。这只说明从当前汇编里数出来的调用没有立刻撑满；漏看一个库函数压栈就会变小。不能写成“栈是安全的”。

片上实测方法，留给 Founder，**未在硬件上执行**，本交付也没有把填充代码编进固件：

1. 在 `system_init` 打开中断之前，用临时固件把 `0xA4`–`0xFF` 写成 `0xE7`。不要改 `0xA4` 以下，那里是队列和直接 RAM。
2. 复位后走第 3 节的三帧，再走第 5 节的连续 9 帧，同时让 2 ms 扫描中断开着。
3. 停机后读内部 RAM。从 `0xFF` 往下找第一个不是 `0xE7` 的单元。用过的深度约等于 `0x100` 减该地址。
4. 预期：高水位停在 `0xA4` 以上，并且和上面的 33 字节同一量级。若 `0xE7` 被写进 `0xA3` 或更低，栈已经盖住队列，这一版不能验收。
5. 测完丢掉临时固件，不要把填充循环留在发布 HEX 里。

直接 RAM 的 1 字节空洞用再小的全局变量也补不上。后续若要加变量，先改内存布局，不要在这份链接结果上继续堆。
